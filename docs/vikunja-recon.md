# Разведка API Vikunja (фаза 0)

**Версия инстанса (`GET /info`): `v2.6.0`.**
Дата прогона: 2026-09-20. Инстанс — self-hosted, адрес и токен в документ не попадают намеренно.
Полигон: проект `Inbox` (id 1), канбан-вью id 4, бакеты `To-Do` (1, default) / `Doing` (2) / `Done` (3, done-bucket).
Пробная задача — id 4, `[newtab-probe] renamed`; оставлена в проекте для проверки веб-редактора (см. ниже).

Прочие поля `GET /info`, которые влияют на дизайн:

```json
{
  "max_items_per_page": 50,
  "concurrent_writes": true,
  "task_comments_enabled": true,
  "webhooks_enabled": true
}
```

## 2. Расхождения с ADR-003 и спекой

Ничего в ADR/спеке не исправлялось — только зафиксировано.

1. **Форма view-эндпоинта.** ADR §Р4(б), §Р5 и спека §6 говорят о `GET /projects/:pid/views/:vid/tasks` как о списке задач. На канбан-вью он отдаёт **массив бакетов с вложенными `tasks[]`** (ключ может отсутствовать у пустого бакета). Zod-схема пулла должна описывать `VikunjaBucketWithTasks[]`, а не `VikunjaTask[]`; бакеты вью и их задачи приходят одним запросом.
2. **Пагинация не учтена нигде.** `max_items_per_page: 50`, `per_page` применяется к каждому бакету, `x-pagination-total-pages` для канбан-вью считает бакеты и непригоден как критерий останова. «Полный пулл» из спеки §6 должен листать `page=1..N` с `per_page=50`, пока хотя бы один бакет возвращает 50 задач.
3. **Точность `updated` как etag.** Спека §5 сравнивает `fresh.updated !== knownEtag` строго. Ответ на `PUT /projects/:id/tasks` и на перенос в бакет содержит наносекунды, следующий `GET` — секунды: `knownEtag`, взятый из ответа мутации, **никогда не совпадёт** с `GET` и даст ложный `conflict` на каждой второй правке. `updated` нужно нормализовать до секунд (например, `Math.floor(Date.parse(v) / 1000)`) перед записью в `remoteRef.updated` и перед сравнением.
4. **Ловушка 6 (`done_at` не проставляется при переносе в done-бакет) на 2.6.0 не воспроизводится** — `done_at` заполняется. Фолбэк на `updated` из спеки §7 остаётся как защита для других версий, но это не основной путь.
5. **Вопрос 2 спеки (форма переноса) закрыт**: работает только `POST /projects/:pid/views/:vid/buckets/:bucketId/tasks` с `{"task_id"}`. Вариант «с `task_id` и `bucket_id` в теле на `…/buckets/tasks`» отдаёт 400.
6. **Выполненные задачи приходят с view-эндпоинта по умолчанию** (лежат в done-бакете). Спека §6 предлагала «запрашивать выполненные явным фильтром» — не нужно; явный `filter=done = true` наоборот **исключает** невыполненные. Единственная оговорка: у вью есть собственное поле `filter` (здесь `null`); если пользователь задал фильтр вью, он применится к пуллу.
7. **`done_bucket_id` / `default_bucket_id` уже лежат в `views[]` ответа `GET /projects`** — `listScopes` может пометить done-бакет и найти канбан-вью без дополнительных запросов; `GET /projects/:id/views/:vid` для этого не обязателен.
8. **Nullable-массивы.** `labels`, `assignees`, `reminders`, `attachments` приходят как `null`, а не `[]`; `related_tasks` — `null` или `{}`. Спека §7 предполагала `labels[]`.
9. **Rate limit отсутствует** (заголовков нет). ADR §Р11 держит 429 → `rateLimited` — оставить как защиту, но реальной ветки тестирования нет.
10. **Токен для разведки — полноправный токен владельца** (`GET /routes` отдаёт все роуты). ADR §8 требует отдельный ограниченный API-токен для расширения: скоупы `tasks`, `tasks_labels`, `projects.read_all` **плюс** `projects.views_buckets_put` / `views_buckets_delete` для достройки колонок мастером — без них шаг «создать недостающие колонки» отвалится 403. Проверено только на полном токене.
11. **HTML-комментарий не переживает веб-редактор** (проверено 2026-09-21: TipTap выбрасывает `<!-- … -->` при сохранении описания). Спека §7 предполагала перенос метаданных в комментарий к задаче (`task_comments_enabled: true`). **Решение: для Vikunja скрытых метаданных не заводить вообще** — ни в описании, ни в комментариях (комментарий на каждой задаче в чужом трекере — тот же «мусор у пользователя», что и автоимпорт из ADR §Р10). Всё, что Trello прячет в `desc`, у Vikunja есть нативно или выводится детерминированно: `localId` ← `vikunja:<task.id>` (глобальный числовой id стабилен), `createdAt` ← `task.created`, `statusChangedAt` ← `done_at` / `updated`. Промежуточные статусы плоского режима (`inprogress` / `struggle`) живут только в локальном сторе виджета (он и так персистентный и по ADR §Р4 «видны только в расширении»); пулл в плоском режиме сохраняет локальный статус известной задачи, пока не изменился `done`. Следствие для задачи 5: вынос `hiddenMetadata` из `trello/mapping.ts` в общий модуль не нужен — у него не будет второго потребителя.

Побочный факт для ADR §2.2: `concurrent_writes: true` в `/info` — оптимистичные блокировки на стороне сервера нет, read-modify-write по-прежнему единственная защита от lost update.
